# Puppeteer Phase 1 Extend: Policy-Owned Task Admission

> **For agentic workers:** This phase extends the completed Phase 1 framework
> refactor. It is still a framework-only phase. Do not add Puppeteer-specific
> TTE, greedy routing, or resource-dependency logic here. The goal is to remove
> the executor's dependency on `ExecutionPlan.compute_order` and make task
> admission fully policy-owned.

## 1. Goal

Phase 1 introduced `SchedulingPolicy` so that admission, path lookup, and
bandwidth allocation can be delegated out of `AnalyticalExecutor`.

However, the current executor still depends on `ExecutionPlan.compute_order` and
maintains per-node compute cursors. This means the executor still embeds one
specific execution-order model:

- compute tasks on each node are serialized by `compute_order`
- only the current cursor task may be emitted
- cursor advancement is hard-coded in `analytical.py`

This phase moves that compute-order logic into `DefaultSchedulingPolicy`.

After this phase:

- executor only checks explicit DAG dependencies
- all dependency-satisfied tasks enter `ready_pool`
- `policy.emit_ready_tasks(...)` decides which tasks may execute
- default C++ reference compute ordering is preserved by default policy
- executor no longer takes `ExecutionPlan` as an execution input

## 2. Relationship to Other Phases

This phase sits between:

- [Phase 1](puppeteer-phase1-plan.md): policy-based executor refactor
- [Phase 2](puppeteer-phase2-plan.md): Puppeteer strategy reproduction

Phase 2 should assume this phase is complete. Puppeteer policy should not rely on
executor-side compute cursors or `ExecutionPlan` input.

## 3. Non-Goals

Do not implement:

- Puppeteer TTE analysis
- Puppeteer greedy route planning
- Puppeteer resource dependency groups
- weighted or priority bandwidth allocation
- new workload schema fields

Do not change workload semantics. `Task.deps` should continue to represent
explicit dependency edges generated by workload builders.

## 4. Current Problem

Before this extension, the execution flow is conceptually:

```text
P2PWorkload
  -> static_analysis
  -> TaskSerializer
  -> ExecutionPlan.compute_order
  -> AnalyticalExecutor(workload, execution_plan)
```

This makes `TaskSerializer` awkwardly placed:

- it is logically an analysis/default-policy component
- but its output is consumed directly by executor internals
- executor becomes tied to per-node compute serialization
- alternative policies cannot fully control task admission

The existing `emit_ready_tasks` hook should be the single place where ready tasks
are admitted into execution. This includes compute ordering.

## 5. Target Architecture

### 5.1 New Execution Flow

Target flow:

```text
P2PWorkload
  -> analysis/strategy builds SchedulingPolicy
  -> AnalyticalExecutor(topology, policy).execute(workload)
```

There is no executor-level `ExecutionPlan` argument.

Default behavior becomes:

```text
DefaultSchedulingPolicy.initialize(...)
  -> build or receive compute order using CppReferenceOrdering
  -> maintain private per-node compute cursors

AnalyticalExecutor
  -> task deps satisfied
  -> add task to ready_pool
  -> policy.emit_ready_tasks(...)
  -> emit returned tasks
```

### 5.2 Executor Boundary

`AnalyticalExecutor` owns:

- event queue
- dependency counters
- dependents map
- ready pool
- active flows
- task timing records
- flow remaining-byte updates

`AnalyticalExecutor` must not own:

- compute ordering
- per-node compute cursor
- C++ reference execution order
- policy-specific admission state

### 5.3 Policy Boundary

`SchedulingPolicy` owns:

- admission rules for ready tasks
- path lookup
- bandwidth allocation
- private bookkeeping needed by the policy

For default behavior, this includes compute ordering.

For Puppeteer behavior later, this can include:

- default compute ordering
- resource-dependency admission for flow tasks
- route table lookup
- TTE-aware bandwidth allocation

## 6. API Changes

### 6.1 Executor API

Current Phase 1-style API:

```python
result = executor.execute(workload, execution_plan)
```

Target API:

```python
result = executor.execute(workload)
```

The executor constructor remains policy-based:

```python
executor = AnalyticalExecutor(
    topology=topology,
    policy=policy,
)
```

### 6.2 Policy Initialization

Current Phase 1 policy initialization may include `execution_plan`:

```python
policy.initialize(workload, topology, execution_plan)
```

Target initialization:

```python
policy.initialize(workload, topology)
```

If a policy needs an ordering plan, it should compute or receive it internally.

### 6.3 SchedulingPolicy Interface

Target interface:

```python
class SchedulingPolicy(ABC):
    def initialize(
        self,
        workload: P2PWorkload,
        topology: NetworkTopology,
    ) -> None:
        ...

    def emit_ready_tasks(
        self,
        current_time: int,
        ready_tasks: list[Task],
    ) -> list[int]:
        ...

    def get_flow_path(self, task: Task) -> list[int]:
        ...

    def allocate_bandwidth(
        self,
        current_time: int,
        active_flows: list[ActiveFlow],
    ) -> dict[int, float]:
        ...

    def on_task_emitted(self, current_time: int, task: Task) -> None:
        ...

    def on_task_completed(self, current_time: int, task: Task) -> None:
        ...
```

Keep the no-heavy-`SimulationState` rule from Phase 1.

## 7. DefaultSchedulingPolicy Design

### 7.1 Responsibilities

`DefaultSchedulingPolicy` should preserve the current default executor behavior:

- shortest-path routing through existing `RoutingHints`
- fair-share bandwidth allocation
- compute tasks serialized according to C++ reference ordering
- flow tasks emitted as soon as their explicit deps are satisfied

### 7.2 Compute Ordering

Reuse existing ordering logic:

- `CppReferenceOrdering`
- or `TaskSerializer` if moving code is not desired in this phase

Recommended direction:

- keep `CppReferenceOrdering` as the reusable core
- avoid writing `ExecutionPlan` JSON during normal execution
- treat `ExecutionPlan` as an optional serialization/debug artifact, not executor
  input

Initialization:

```python
class DefaultSchedulingPolicy(SchedulingPolicy):
    def initialize(self, workload, topology):
        self.compute_order = CppReferenceOrdering().order(workload)
        self.compute_position = {
            task_id: index
            for node, ids in self.compute_order.items()
            for index, task_id in enumerate(ids)
        }
        self.compute_cursor = defaultdict(int)
```

### 7.3 Admission Logic

Default admission:

```text
for each task in ready_tasks:
  if flow:
    emit
  if compute:
    emit only if it is the current cursor task for its node
```

Pseudo-code:

```python
def emit_ready_tasks(self, current_time, ready_tasks):
    emitted = []
    for task in sorted(ready_tasks, key=self._stable_key):
        if task.is_flow():
            emitted.append(task.task_id)
            continue

        if task.is_compute() and self._is_next_compute(task):
            emitted.append(task.task_id)
    return emitted
```

`_stable_key` should keep deterministic behavior in tests. A safe default is
`task.task_id`.

### 7.4 Cursor Advancement

Advance compute cursor in policy notification:

```python
def on_task_completed(self, current_time, task):
    if task.is_compute():
        self.compute_cursor[task.node] += 1
```

The executor must call `_drain_ready_pool(current_time)` after task completion,
because a compute task previously held in `ready_pool` may become admissible when
the cursor advances.

## 8. Executor Refactor Details

### 8.1 Remove ExecutionPlan Dependency

Remove from `AnalyticalExecutor.execute`:

- `plan` argument
- `compute_cursor`
- direct access to `plan.compute_order`
- checks for "next compute in compute_order"

The executor should not distinguish "next compute" from other ready tasks.

### 8.2 Ready Pool Rule

When any task's explicit dependency count reaches zero:

```text
add task_id to ready_pool
drain_ready_pool(current_time)
```

This applies to both compute and flow tasks.

Do not apply executor-side compute-order filtering.

### 8.3 Drain Rule

`_drain_ready_pool(current_time)` should:

1. convert ready ids to `Task` objects
2. call `policy.emit_ready_tasks(current_time, ready_tasks)`
3. validate returned ids are currently in `ready_pool`
4. emit each returned task
5. leave non-emitted tasks in `ready_pool`

Emission behavior:

- compute task: record start time and schedule `compute_done`
- flow task: record start time, query `policy.get_flow_path`, create `ActiveFlow`

### 8.4 Completion Rule

On compute or flow completion:

1. record end time
2. release explicit dependents
3. call `policy.on_task_completed`
4. drain ready pool again

Order matters. If default policy advances compute cursor in
`on_task_completed`, then draining after the notification allows the next compute
task to start at the same timestamp.

### 8.5 Deadlock Detection

At the end of event processing:

- if event queue is empty and `ready_pool` is non-empty, ask the policy for no
  further hidden state; raise a clear error

Error should include:

- current time
- pending ready task ids
- policy class name

This catches policies that hold tasks forever.

## 9. Static Analysis and TaskSerializer Repositioning

### 9.1 New Role

`task_serializer.py` should no longer be required by executor.

It can remain as:

- a reusable default ordering implementation
- a JSON export/debug utility
- a compatibility utility for scripts that still want to inspect compute order

But normal end-to-end execution should not be:

```text
TaskSerializer -> ExecutionPlan -> executor
```

It should be:

```text
DefaultSchedulingPolicy -> internal compute_order -> executor admission
```

### 9.2 Possible File Organization

Minimal-change option:

- keep `CppReferenceOrdering` in `static_analysis/task_serializer.py`
- import it from `DefaultSchedulingPolicy`
- stop using `ExecutionPlan` in executor path

Cleaner later option:

```text
src/static_analysis/passes/compute_ordering.py
  CppReferenceOrdering
  OrderingStrategy

src/static_analysis/task_serializer.py
  ExecutionPlan JSON serialization wrapper
```

Do not require the cleaner move in this phase unless it is low-risk.

## 12. Tests

Required checks:

```bash
pytest tests/test_analytical_executor.py -v
pytest tests/test_executor_policy.py -v
pytest tests/test_task_serializer.py -v
pytest tests/ -v
```

Important scenarios:

1. Two compute tasks on the same node with no explicit deps still run in default
   C++ reference order.
2. Two compute tasks on different nodes can run concurrently if admitted by
   policy.
3. A flow task with satisfied deps is emitted immediately by default policy.
4. A custom policy can emit compute tasks in a different valid order without
   changing executor code.
5. Default end-to-end task timings match the pre-extension executor behavior.
6. Executor raises a clear error if a policy leaves ready tasks pending forever.

## 13. Acceptance Criteria

Phase 1 Extend is complete when:

- `AnalyticalExecutor.execute` no longer accepts `ExecutionPlan`
- `analytical.py` has no per-node compute cursor logic
- default compute ordering is enforced by `DefaultSchedulingPolicy`
- existing default behavior and task timings are preserved
- normal scripts no longer require `TaskSerializer` before executor execution
- `TaskSerializer` is documented as an optional ordering/serialization utility
- Phase 2 policies can own all admission decisions through `emit_ready_tasks`

## 14. Handoff Notes

This extension makes `emit_ready_tasks` the single admission abstraction.

Future strategy agents should follow this rule:

> If a task is dependency-satisfied but should not start yet, keep it in
> `ready_pool` by not returning it from `emit_ready_tasks`.

Do not reintroduce executor-side assumptions about compute order, pipeline
stages, resource barriers, or policy-specific sequencing.
